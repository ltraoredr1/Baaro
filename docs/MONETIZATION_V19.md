BAARO Economy

BAARO Economy is the server-authoritative creator-revenue and payout layer. It uses fiat amounts in internal minor units and does not reintroduce a cryptocurrency or a transferable crypto wallet.

Revenue sources

The economy layer is intended to account for creator and platform revenue generated by:

- Tips
- Creator subscriptions
- Marketplace orders
- Live tickets and paid training
- Advertising revenue events
- Commercial campaigns and other products when their server-side fulfillment path is enabled

Creator Rewards points are a separate engagement system. They are not cash, cannot be withdrawn, and must not be added to the cash ledger.

Not every monetization product is necessarily enabled for public launch. A product is payable only when its server-side payment verification and fulfillment path is implemented and configured.

Financial rules

- Amounts are stored as integer minor units. Currency and provider conversion must be explicit.
- The browser must not write directly to the economy ledger or change an authoritative balance.
- Revenue shares are controlled server-side through "economy_policies".
- Revenue events must be idempotent.
- Creator earnings move through pending and available states according to server-side verification and settlement.
- A payout request reserves available funds before transfer execution.
- Only trusted server code using the service role may complete or cancel a payout.
- Payouts are subject to minimum cash-out, KYC and risk controls.
- BAARO Credits remain closed-loop product credits: no cash-out, peer transfer or conversion to XOF.

Payment and revenue flow

1. A customer starts a checkout through "/api/payments". Prices and entitlements must be resolved and validated server-side.
2. The payment provider processes the payment.
3. The payment webhook independently verifies the provider result, expected amount and currency before settling the relevant order or entitlement.
4. Where the product generates creator revenue, the server records an idempotent economy event through "record_economy_event".
5. Creator revenue remains pending until the applicable server-side settlement checks make it available.
6. The creator requests a withdrawal from Revenus. The authenticated request calls "request_economy_payout", which reserves the amount in the ledger.
7. For Mobile Money, "/api/payouts" starts a CinetPay Transfer when "CINETPAY_TRANSFER_TOKEN" is configured. "/api/payout-webhook" re-queries CinetPay and then calls "complete_economy_payout" or "cancel_economy_payout".
8. If the transfer is not configured, the Mobile Money reservation is cancelled rather than silently treated as paid.

Payout methods and operational limits

- Mobile Money: automated CinetPay Transfer is supported when the transfer token and public notification URL are configured.
- Bank transfer: the current API path marks a request for manual processing. This is not an automated bank integration or proof of a completed bank transfer.
- KYC/risk: payout eligibility depends on the verified creator payout profile and risk controls.
- Production readiness: static checks do not prove that merchant credentials, provider accounts, webhook URLs, KYC review, settlement or payout destinations are operational. End-to-end tests are required before public launch.

Advertising revenue bridge

"/api/ad-revenue" is a server-only endpoint protected by "BAARO_AD_REVENUE_SECRET". It validates revenue amounts and records the event through "record_ad_creator_revenue".

The calling ad-delivery system must authenticate server-to-server and supply a stable idempotency key. Never expose the secret in client code.

Required production configuration

Configure only the secrets for providers actually enabled:

- Supabase server credentials ("SUPABASE_URL", "SUPABASE_SERVICE_ROLE_KEY") and the public credentials required by the authenticated API flow.
- "CINETPAY_API_KEY" and "CINETPAY_SITE_ID" for CinetPay pay-in.
- "CINETPAY_TRANSFER_TOKEN" for automated CinetPay Mobile Money payouts.
- "PUBLIC_APP_URL" (or the supported deployment URL fallback) for payout notifications.
- "STRIPE_SECRET_KEY" and "STRIPE_WEBHOOK_SECRET" when Stripe is enabled.
- "BAARO_AD_REVENUE_SECRET" when an external ad-delivery service sends creator revenue events.
- Upstash Redis credentials when production rate limiting uses Upstash.

Never commit production secrets or put them in "VITE_*" client-exposed variables.

Database and checks

The economy schema and RPC definitions are expected in "supabase/migrations/0001_baaro_unified.sql".

The repository checks in "scripts/check-economy.mjs" and the real-money flow checks inspect this migration when it exists. If it is absent, migration-specific assertions are skipped with a warning.

A green interface/static check alone therefore does not validate the deployed Supabase schema, RLS policies, RPC permissions or production data.

Run the economy, payout and real-money checks after changes, and separately verify that the deployed database has the matching migration and policies.
